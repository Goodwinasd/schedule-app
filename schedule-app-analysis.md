## 1. Что это за проект

Однопользовательское (единственный администратор) веб-приложение для составления и публикации расписания колледжа/техникума.

**Стек:** Flask + SQLite (WAL) + Alembic, ванильный JS SPA (ES-модули, без сборщика), экспорт в XLSX/DOCX/PDF (`openpyxl`, `python-docx`, `reportlab`), Swagger (`flasgger`), фоновые задачи (`APScheduler`).

**Функциональность (реально реализованная):**

| Домен | Что есть |
|---|---|
| Справочники | группы (курс, специальность, заочка), преподаватели (телефон, аудитория по умолчанию), предметы (преподаватель по умолчанию), аудитории, специальности |
| Учебные планы | `curriculum` (часы, недели, семестр, цикл, форма контроля), копирование плана специальности, прогресс/темп |
| Расписание | недели Пн–Сб, пары 1–8, подгруппы, проверка конфликтов (преподаватель/аудитория/дубль группы), перенос, история изменений |
| Генератор | автозаполнение недели по плану: приоритет отстающим предметам, seeded-перемешивание, «дрейф» первой пары, ограничение 4 пары в будни / 3 в субботу, замены преподавателей (отсутствия), зеркалирование составных потоков (`02-0923+11/24`), исключение праздников и 1 сентября для 1 курса |
| Публикация | черновик/опубликовано по дню и по неделе; публичный просмотр видит только опубликованное |
| Корзина | мягкое удаление всего (`deleted_at`), восстановление с проверкой конфликтов, автоочистка через 30 дней |
| Экспорт | XLSX/DOCX/PDF по группе/преподавателю/аудитории + сводный Excel по всем группам |
| Админ | импорт справочников из Excel с синонимами заголовков, шаблоны, бэкап/восстановление БД, проверка сиротских записей, диагностика `PRAGMA integrity_check`, настройки, схема звонков (3 пресета) |

Масштаб: ~8 тыс. строк, из них 3.6 тыс. — один `routes.py`, 3.6 тыс. — 16 JS-модулей, 3 тыс. — CSS.

## 3. Как это устроено

**Поток запроса:** `app.py` → Blueprint в `routes.py` → `get_db()` (`sqlite3.Connection` с подклассом-таймером медленных запросов) → SQL строками → `jsonify`.

**Аутентификация:** один пароль из `.env` → хеш `generate_password_hash` считается **на каждом старте** → сессия Flask (`session['is_admin']`) → CSRF-токен в сессии, обязательный заголовок `X-CSRF-Token` на всех `POST/PUT/DELETE /api/*` (кроме `/api/auth/*`).

**Схема БД — два источника правды:** Alembic-миграции **и** функции `ensure_curriculum_table`, `ensure_teacher_tables`, `seed_specialties`, `fix_lessons_group_id` в `db.py`, которые создают/дополняют таблицы в обход миграций.

**Кэш:** `refs_cache = TTLCache(300)` — списки справочников на 5 минут, инвалидация по префиксу при записи.

**Frontend:** глобальный мутабельный синглтон `state.js`, событийная шина на `window` CustomEvent `DATA_MUTATED` (4 независимых подписчика), ~60 функций вынесены в `window` для inline-обработчиков, админ-режим — чисто клиентский (`state.isAdmin`), сервер проверяет сессию отдельно.

**Генератор:** жадное размещение `weekly = ceil(hours / (weeks*2))` пар с приоритизацией по «дельте темпа», детерминированный `random.Random` от `ISO-год_неделя_группа`, затем построчная посадка в день с fallback-периодами и защитой от бесконечного цикла (`block_attempts > 40`).

## 4. Что сделано хорошо

1. **Все write-эндпоинты закрыты** `@login_required` + CSRF (сверены все 68 декораторов `@bp.route` — ни одного write-маршрута без проверки сессии).

3. **Переиспользуемая валидация конфликтов** — одна и та же логика работает и в API, и в генераторе.
4. **Настоящие миграции Alembic**, линейная цепочка без ветвлений, ровно один head.

6. **Зрелые решения для SQLite:** WAL, `busy_timeout=10s`, `mmap_size`, логгер медленных запросов (`db.py:17-47`).
7. **Документирующие docstring** с YAML для Swagger на большинстве маршрутов, комментарии по-русски объясняют нетривиальные решения (защита от зацикливания генератора, зеркалирование потоков).
8. **Продуманный UX-слой:** скелетоны загрузки, тосты, шаблоны Excel с синонимами заголовков, публикация черновиков, корзина, тёмная тема.

## 5. Критические дефекты (P0 — ломают данные/безопасность)

### 5.1. Восстановление БД из файла не работает — две независимые ошибки

- **Backend:** `routes.py:3177` — `refs_cache.invalidate_all()`, но в `cache.py:24-33` есть только `invalidate()` и `invalidate_prefix()` → `AttributeError` → 500. Причём файл к этому моменту **уже записан поверх рабочей БД** и проверен на целостность: пользователь видит ошибку при фактически выполненном восстановлении.

**Исправление:** `refs_cache.invalidate()`; в JS — `import state from './state.js'` (и вообще брать токен из `api.js`). Закрыть тестом — сейчас `/api/admin/backup/restore` не покрыт вообще.

### 5.2. Реальный секрет в примере конфига
`.env.example:4` содержит **тот же самый** `SCHEDULE_SECRET_KEY`, что и боевой `.env`, а `.env.example:1` — `SCHEDULE_PASSWORD=Admin123!`. `.env.example` в `.gitignore` не входит → ключ подписи сессий фактически опубликован (подделка админ-сессии, если проект куда-то утечёт/уедет в архив/репозиторий). Боевой пароль в `.env` — `admin123!`, то есть минимально допустимый.

**Исправление:** ротировать `SCHEDULE_SECRET_KEY` и пароль, в примере — плейсхолдеры (`change-me`), добавить в `config.py` предупреждение при использовании дефолтного ключа.

### 5.3. Публичная выдача персональных данных
`generic_crud` (`routes.py:502-522`, вызов для преподавателей — `routes.py:2212`) делает `SELECT *` и отдаёт **телефоны преподавателей** без авторизации: `GET /api/teachers`. **Исправление:** закрыть справочники `@login_required` (публичному просмотру расписания они не нужны — расписание отдаётся по имени группы), либо явно перечислять колонки без `phone`.

### 5.4. `sys.exit(1)` при импорте конфига
`config.py:26-33` валидирует пароль и **завершает процесс** на этапе импорта модуля; `config.py:36-40` дописывает сгенерированный ключ в `.env`. Следствия: приложение нельзя импортировать в WSGI-контейнер без `.env`, ошибка конфигурации выглядит как «молчаливый» выход, любой инструмент, импортирующий `app` (тот же pytest без переменных окружения), падает целиком.

**Исправление:** вынести валидацию в функцию `create_app()` / точку входа, бросать `RuntimeError` с внятным текстом; автогенерацию ключа — логировать.

### 5.5. Docker/прод-контур
- `Dockerfile:12` — `CMD ["python", "app.py"]`: **dev-сервер Werkzeug** (не для продакшена), `gunicorn` отсутствует в `requirements.txt`, контейнер работает от **root**, нет `HEALTHCHECK`.
- `.dockerignore` **не исключает** `data/` и `backups/` → в образ попадают боевая SQLite-БД и 18 бэкапов (включая те, что с персональными данными). Это же ломает воспроизводимость сборки.
- `docker-compose.yml` — нет healthcheck, только `FLASK_HOST`, `env_file: .env` жёстко обязателен.

## 6. Серьёзные дефекты (P1)

### 6.1. Нет валидации входных параметров → 500 вместо 400
Системно: `int(...)` и `datetime.strptime(..., '%Y-%m-%d')` без обработки исключений.
- `/api/teacher-schedule?teacher_id=abc` → `routes.py:1208`;
- `/api/teacher-schedule-table`, `/api/classroom-schedule-table` → `2174`, `2204`;
- все эндпоинты с `monday` → `build_week_dates` (`routes.py:80-83`): `/api/schedule-table`, `/api/availability`, `/api/export`, `/api/schedule/export/excel`, `/api/week` (DELETE), `/api/week/restore`, `/api/week/publish`, `/api/schedule/clear-week`, `/api/schedule/restore-week`;
- `PUT /api/days/<id>` → `KeyError` на `data['day_name']` (`routes.py:1631`) и полное отсутствие валидации даты.

### 6.2. «Удалить неделю преподавателя/аудитории» уничтожает чужие расписания
`routes.py:1383-1398`: для `target_type=teacher|classroom` мягко удаляются **все уроки всех групп** на этой неделе, где занят преподаватель/аудитория. Счётчики (`affected`, `pairs_affected`) считают все записи с `deleted_at IS NOT NULL` без привязки к моменту удаления → цифры в UI завышены. Аналогично `restore_week` (`1436-1445`).

### 6.3. `PUT /api/lessons/<id>` затирает поля при частичном теле
`routes.py:1910-1946`: `subject_id`, `teacher_id`, `classroom_id`, `group_id`, `subgroup` берутся из тела безусловно; отсутствующий ключ → `NULL`. Любой клиент, отправивший только `{day_id, period}` (drag&drop), обнулит урок. Семантика PATCH не поддерживается.

### 6.4. Мягкое удаление портит исходные метки
`delete_day` (`routes.py:1654`) обновляет `deleted_at` у **уже удалённых** уроков (нет `AND deleted_at IS NULL`) — теряется исходное время удаления, корзина и автоочистка врут. В `delete_week`/`clear_week_group` этот фильтр есть — несогласованность.

### 6.5. `restore_lesson` восстанавливает урок в удалённый день
`routes.py:2013-2018`: проверяется только конфликт слота, статус дня (`schedule_days.deleted_at`) не проверяется → «невидимый» урок (день в корзине, урок активен).

### 6.6. Настройки не применяются (частично или совсем)
`config.py:112-117` фиксирует значения на момент импорта.
- `login_rate_limit`, `login_rate_window`, `backup_retention_days` после изменения работают только частично (что-то читается через `SETTINGS`, что-то из константы `TRASH_RETENTION_DAYS = 30`).
- **`session_lifetime` не влияет ни на что:** `session.permanent` не устанавливается нигде (поиск по всему проекту) → `permanent_session_lifetime` не действует, кука живёт до закрытия браузера. Настройка в UI — фикция, при этом она покрыта тестами.

### 6.7. Две конкурирующие системы бэкапов
`create_backup()` (`db.py:209-229`): `db_backup_*.sqlite`, хранит **10** последних. `_maybe_create_backup()` (`app.py:65-75`): `schedule_backup_*.db`, раз в сутки, удаление по `backup_retention_days`. Итог — 20 файлов двух видов и две противоречащие политики хранения (фактически в `backups/` уже 20 файлов).

### 6.8. Фоновые задачи не работают вне `python app.py`
`app.py:95-110`: `BackgroundScheduler` (бэкапы каждые 6 часов) и `_cleanup_old_deleted()` запускаются **только** под `__main__`. Под gunicorn/WSGI (и в Docker, если перейти на нормальный сервер) бэкапов и очистки корзины нет вовсе. Под dev-сервером с релоадером планировщик может дублироваться.

### 6.9. Пользовательская схема звонков игнорируется в «свободных окнах»
`routes.py:2960`: `periods = [... for b in BELL_SCHEDULE]` — константа из конфига, тогда как `/api/schedule-table` и экспорт используют `get_bell_schedule()`. Админ меняет звонки, а аналитика и статистика нагрузки считаются по старой схеме.

### 6.10. PDF-экспорт падает на «плохих» символах и теряет кириллицу в Linux
`routes.py:450-454`: текст вставляется в `reportlab.Paragraph` без экранирования → `&`, `<` в названии группы/предмета дают 500. Шрифт ищется по путям Windows/Linux (`400-414`); в `python:3.13-slim` их нет → `Helvetica` без кириллицы (кракозябры) в Docker.

### 6.11. Загрузки без ограничений и без проверки схемы
`routes.py:3164`: `f.save(DB_PATH)` — размер не ограничен, схема не проверяется (только `integrity_check`, который проходит и на «чужой» БД) → приложение падает на всех запросах после такого восстановления. Аналогично импорт Excel (`3243-3342`) — без лимита размера.

### 6.12. Генератор: неограниченный `week_count` и синхронная работа
`routes.py:3352-3358`: верхняя граница `4` действует только для алиаса `weeks_count`; `week_count` принимается любым (`max(int(...), 1)`). Один запрос может сгенерировать сотни недель в рамках HTTP-запроса, с несколькими SQL-запросами на каждую пару.

### 6.13. XSS через данные из БД
`ui.js:517` (`${g.name}` в `<option>`, соседние строки экранированы через `escapeHtml`), `ui.js:534` (`day_name`), `ui.js:828` (`p.start/p.end`), `modal.js:41` (`showKimiAlert` — в него попадают серверные ошибки с именами групп, `settings.js:224,252`, `nav.js:302,332`), `trash.js:48`, `settings.js:224,252`. Имена групп/преподавателей приходят из Excel-импорта → хранимый XSS реален, хоть и требует админского действия.

### 6.14. `api()` не переживает не-JSON ответы
`static/js/modules/api.js:26-27`: `await res.json()` без проверки `content-type` и без `try/catch` → HTML-страница 500/502 превращается в необработанный reject. `showLoader()` без `finally` (`settings.js:88-92`, `trash.js:8-10`, `ui.js:249-253`) → вечный блокирующий оверлей. Нет таймаута/`AbortController`, нет обновления CSRF-токена после протухания сессии (все записи навсегда 403 до перезагрузки).

### 6.15. Публичные «тяжёлые» эндпоинты без rate limit
`/api/export` (PDF/DOCX/XLSX) и `/api/schedule/export/excel?type=all` (лист на каждую группу, N×запросы) доступны без авторизации. В сочетании с отсутствием лимитов — тривиальный способ положить сервер.

## 10. Методика и ограничения

- Прочитаны полностью: `app.py`, `config.py`, `db.py`, `utils.py`, `generator.py`, `schedule_balancer.py`, `cache.py`, все 13 миграций, `conftest.py`, CI, Docker-файлы, `.bat`, `requirements*`, `.env.example`; `routes.py` — выборочно по риск-зонам (аутентификация, CRUD, валидация, экспорт, админ/бэкапы, генератор) ≈ 60% файла, список маршрутов — полностью; frontend — все 16 модулей (через параллельный аудит с проверкой ключевых мест вручную), `index.html`, `style.css` (по грепам).

Все выводы — статический анализ; формулировки «падает/не работает» означают дефект в логике (кроме случаев, где ошибка однозначна: отсутствующий метод `invalidate_all`, пустой CSRF-заголовок, `sys.exit` при импорте).
- Проверено выборочно на достоверность: ни один write-маршрут (из 68 декораторов `@bp.route`) не остался без `@login_required`; цепочка миграций линейна, один head; `.git` в проекте отсутствует; `session.permanent` не используется нигде.
- Тестовые прогоны не подтверждены; заявленное в документации «144 теста проходят» не проверялось.
