# schedule-app: план под ~200 одновременных пользователей

Цель: приложение держит ~200 одновременных сессий (≈100 активно правят расписание, ≈100 только смотрят), не падает, изменения не теряются. Хостинг пока не выбран → решения должны быть переносимы между Windows и Linux.

---

## 1. Замеры (что уже есть)

Сделаны на текущем коде, живой сервер `flask run`, БД `data/schedule.db` (6872 занятия, 8019 дней).

| Сценарий | rps | p50 | p95 | ошибок |
|---|---|---|---|---|
| 10 параллельных чтений | 394 | 22 мс | 38 мс | 0 |
| 50 параллельных | 379 | 131 мс | 154 мс | 0 |
| 100 параллельных | 361 | 271 мс | 305 мс | 0 |

| Запись (SQLite WAL, timeout=10 c, копия БД) | результат |
|---|---|
| 16 потоков × 20 вставок | 320/320, 0 locked, **487 записей/с** |
| 64 потока × 20 вставок | 1280/1280, **0 locked**, **244 записи/с** |

**Вывод.** Пропускная способность одного процесса ≈ 380 rps — примерно и есть потолок для 200 живых пользователей SPA. Записи в SQLite держат 244–487/с, а 100 редакторов при среднем темпе 1 правка / 10 с дают ~10–20 записей/с, то есть 4–8 % возможностей БД. **Сам SQLite — не узкое место.** Падать будет на четырёх других вещах.

## 2. Почему упадёт (по коду)

1. **Долгие транзакции в HTTP-запросе.**
   `routes.py:3345` генерация недели — сотни `INSERT` в одном `BEGIN IMMEDIATE`; `routes.py:3432` `clear-week` — массовый `UPDATE`; `routes.py:2687` экспорт «все группы» — лист на каждую из 37 групп; `routes.py:3152` восстановление БД. Пока такая операция идёт, все остальные писатели ждут на файловой блокировке, а воркер занят.

2. **Глобальное состояние в памяти процесса.**
   `routes.py:44-57` — `_login_attempts`, `_last_cleanup_time`; `cache.py` — `refs_cache` (TTL 300 с). Под несколькими воркерами лимит логина и инвалидация кэша распадаются на независимые копии. Симптом: **«изменения не сохраняются»** — на самом деле сохранились, но другой воркер 5 минут отдаёт старую копию справочника.

3. **Лимит логина привязан к IP.**
   `routes.py:1022` — `ip = request.remote_addr`, `login_rate_limit=5`. За nginx/Caddy без `ProxyFix` все 200 человек будут с одного IP: 5 опечаток блокируют **всю школу** на 5 минут. А с `ProxyFix` лимит станет глобальным. Нужен счётчик на пользователя, а не на IP.

4. **Гонки между редакторами.**
   `routes.py:1910-1946` — `PUT /api/lessons/<id>`: последняя запись молча побеждает, отсутствующие в теле поля затираются в `NULL`. Версионирования нет, `updated_at` не проверяется. При 100 редакторах это штатная потеря чужих правок.

5. **Нет модели пользователей.**
   Один пароль на всех (`config.py:42`), `session['is_admin']` — булев флаг, `lesson_history` не пишет, **кто** изменил. Разграничения «смотрит / правит / админ» нет; аудита нет; отозвать доступ одному человеку нельзя.

6. **Инфраструктура «на ноутбуке».**
   `app.py:95-110` — dev-сервер Werkzeug и планировщик в одном процессе; `app.py:33-39` — `/static/*` с `Cache-Control: no-store` (каждый заход заново тянет 16 JS-модулей); `db.py:216` — бэкап `shutil.copy2` по живому WAL (риск битой копии); нет TLS, нет reverse proxy, нет супервизора (упал процесс — сайт лежит).

## 3. Целевая архитектура

```
клиенты (200)
   │  HTTPS
┌──▼──────────────────┐
│ nginx / Caddy       │  TLS, gzip, статика, таймауты, лимит тела
└──┬──────────────────┘
   │ HTTP 127.0.0.1
┌──▼──────────────────┐
│ waitress (Win)      │  N воркеров × M потоков
│ gunicorn (Linux)    │
└──┬───────────┬──────┘
   │           │
   │           └──► очередь задач (jobs-таблица или Redis): генерация,
   │                массовый экспорт, restore, бэкап
   │
┌──▼──────────────────┐     ┌────────────────────────┐
│ SQLite (WAL)        │ или │ PostgreSQL 16          │
│ 1 инстанс, короткие │     │ несколько инстансов    │
│ транзакции          │     │ row-level locking      │
└─────────────────────┘     └────────────────────────┘
   ▲
   └── общее состояние (лимиты, инвалидация кэша) — в БД или Redis
```

Ключевые инварианты:
- HTTP-запрос **никогда** не выполняет работу длиннее ~200 мс; всё тяжёлое — в очередь с прогрессом.
- Любая запись — короткая транзакция, без внешних вызовов внутри.
- Общее состояние — вне памяти процесса.
- Каждая правка несёт пользователя (`changed_by`) и версию строки.

## 4. Этапы

### Этап 1 — «не падать» (1–2 дня)

| Задача | Файлы | Приёмка |
|---|---|---|
| WSGI-сервер вместо dev: `waitress` (Windows) / `gunicorn` (Linux), 4–8 потоков | `Dockerfile`, `run.bat`, новый `wsgi.py` | 100 параллельных чтений без ошибок, p95 < 400 мс |
| Reverse proxy + TLS | `nginx.conf` / `Caddyfile` | HTTPS, gzip, `/static` отдаёт прокси |
| Кэш статики вместо `no-store`; `?v=<hash>` | `app.py:33-39`, `index.html` | повторный заход не тянет JS-модули |
| Бэкап через `VACUUM INTO` (атомарная копия WAL) | `db.py:209-218` | копия открывается, `integrity_check = ok` |
| Планировщик — отдельным процессом, не в веб-воркере | `app.py:101` | при 4 воркерах бэкап ровно один |
| Таймаут и лимит размера на экспорт/импорт/restore | `routes.py:2596,2687,3152,3243` | запрос 100 МБ отклоняется 413 |
| `ProxyFix` + лимит логина на пользователя, не на IP | `routes.py:1022`, `app.py` | 5 ошибок одного логина не блокируют других |

### Этап 2 — «не терять правки» (4–6 дней)

| Задача | Файлы | Приёмка |
|---|---|---|
| Таблица `users` + роли `viewer`/`editor`/`admin`, хеши паролей | `config.py`, `routes.py`, миграция | два разных человека входят под своими учётками |
| `changed_by` в `lesson_history`; аудит входов и правок | `routes.py`, миграция | по любой правке видно, кто и когда |
| `version` у `lessons` + `If-Match`/409 при конфликте | `routes.py:1864`, миграция | два редактора на одну ячейку: второй получает 409, а не тихую перезапись |
| Починить частичный `PUT` (не затирать отсутствующие поля) | `routes.py:1910-1946` | `{day_id, period}` не обнуляет преподавателя/аудиторию |
| Лимиты и инвалидация кэша — в БД (счётчик версии справочников) | `cache.py`, `routes.py` | правка справочника видна всем воркерам сразу |
| Генерация/массовый экспорт/restore — в очередь задач с прогрессом | `routes.py:3345,2687,3152` | во время генерации записи остальных не блокируются |
| Уникальные индексы против двойного бронирования | миграция | параллельные вставки в один слот дают 409, а не дубль |

### Этап 3 — «масштаб и переносимость» (1–2 недели, по потребности)

| Задача | Зачем | Приёмка |
|---|---|---|
| PostgreSQL 16 | снять единственного писателя, несколько инстансов, нормальный бэкап | тот же набор тестов зелёный на PG |
| Перевод SQL: `?` → `%s`, `datetime('now')` → `now()`, `lastrowid` → `RETURNING` | ~40 мест + `db.py` + `alembic/env.py` | нет `sqlite3`-специфичных конструкций в рантайме |
| Docker Compose (app + nginx + db) | переносимость Win/Linux | `docker compose up` даёт рабочее приложение |
| Нагрузочный сценарий «100 редакторов» | проверка перед выкатом | 0 ошибок, p95 записи < 300 мс |

**Когда PostgreSQL обязателен:** больше одного инстанса приложения, либо появление реальных блокировок записи при 100 редакторах. Пока этого нет — этапы 1–2 решают задачу на SQLite.

## 5. Что НЕ делать

- Не разбивать `routes.py` на blueprint'ы «заодно» — отдельная задача.
- Не включать `debug=True` и не оставлять dev-сервер «на время».
- Не делать `full-access` дефолтом в агенте: под ним ничто не защищает `data/` и `backups/`.
- Не переносить на PostgreSQL до этапов 1–2: смена БД не лечит гонки и потерю полей.

## 6. Риски

| Риск | Смягчение |
|---|---|
| Потеря данных при смене БД | миграция со сверкой количества строк по каждой таблице, бэкап до/после |
| Кэш воркеров расходится | инвалидация через общий счётчик в БД, тест «правка видна сразу» |
| 100 редакторов правят одну и ту же неделю | версионирование + 409 + понятное сообщение «обновите страницу» |
| Агент случайно тронет `data/`/`backups/` | политика `workspace-write`, запрет `full-access` по умолчанию |

## 7. Как проверять

1. Чтение: 100 параллельных клиентов на `/api/schedule-table` — 0 ошибок, p95 < 400 мс.
2. Запись: 100 потоков по 10 правок на **копии** БД — 0 `database is locked`.
3. Совместная правка: два клиента меняют один урок → второй получает 409.
4. Долгая операция: запустить генерацию недели и одновременно 20 правок → правки не висят.
5. Отказоустойчивость: убить воркер — сервис отвечает (супервизор поднимает).
